## 3. Active files (touched this session — what changed and why)

**`apps/server/src/routes/orders.ts`** — **A196**. In the **void** handler, right after the order
is marked `voided`, delete the order's kitchen ticket(s) `.eq('order_id', orderId)` (by order id,
so a multi-station order clears fully). In the **refund** handler, before the success response,

## 5. Failed attempts / dead ends (so nobody re-walks them)

- **The "A154/A198 don't work on prod" saga — it was DEPLOY, not code (cost the most time).**
  Symptoms: the admin Migrations panel 404'd and the A198 enrol card didn't render, on prod, while
  dev worked. Two false leads chased: (a) "the fix has a bug" — re-read the committed code line by
  line, it was correct and built; (b) "browser/CDN cache" — a hard refresh didn't fix it. The actual
  cause, proven by a read-only probe: `swiftpos-prod-mype` returned **404** for `/api/admin/migrations`
  (route absent) while returning 401 for older routes and 200 for `/health` → **the prod server was
  up but running a stale build.** The Render deploy had **failed silently**, leaving the old build
  live. A successful redeploy from `main` flipped the route to 401 and fixed both symptoms at once.
  *Lesson: a route that 404s on prod but 401s on dev = stale prod server, full stop.*

- **Prod was serving `dev`, not `main`.** Earlier in the thread, read-only probes showed prod already
  had `dev`-only routes (kds-token, bulk-track) — because its Render service was wired to `dev`. When
  the wiring was "fixed" to `main`, `main` was 94 commits behind `dev` and lacked the batch, so prod
  regressed until `dev`→`main` was merged. *Lesson: know which branch each target deploys from before
  you reason about what's live; it's not in the repo.*

- **A151 rebuild trap — avoided by sweeping source first.** Trusting the stale register text would
  have meant rebuilding split-bill that already exists. (Rule 17.)

- **Do NOT flip the split-bill `/pay` leg-sum check to a 400.** `checkPaymentIntegrity` on the
  `/pay` path is **deliberately log-only** (`[payment-mismatch]`) — a documented pilot decision,
  because an enforcement bug would refuse a real sale mid-service. The takeaway create path
  (`POST /orders`) already reconciles legs to the total and aborts (finding #15); the `/pay` flip
  waits for a week of live `[payment-mismatch]` data + owner go-ahead. The client-side panel already
  blocks a mis-summed set, so the money risk is contained.

- **Schema gates have two different schema sources — know which one fires.** `schema-audit.py`
  checks server selects against `scripts/schema-index.json` (a **live-DB** snapshot — goes stale when
  a migration adds a column; fix = regenerate). `check-api-schema-drift.mjs` builds its schema from
  **migration files** in PGlite (misses runner-bootstrapped tables; fix = allowlist with an ID). We
  hit both this session (migration 92 column; `schema_migration_runs` table). Different fixes.

## 7. Deploy & verify runbook (reusable — run after EVERY deploy)
Read-only, no auth, no writes. `API` = the target's base URL.
```
curl -s "$API/health"                                  # expect 200, db:up, schema:ok
                                                       # prod withholds version/env → NODE_ENV=production
curl -s -o /dev/null -w "%{http_code}\n" \
  -X GET "$API/api/admin/migrations"                   # 401 = new build live · 404 = STALE build
curl -s -o /dev/null -w "%{http_code}\n" \
  -X POST "$API/api/kitchen/kds-token"                 # control: 401 (present) vs 404 (missing)
```
`/health/schema` (200/`missing:[]`) proves migrations 33–38 only — it does **not** cover 92/95/96
(92 is a column not in its list; 96 is an FK). Those are confirmed only by function (a void that
doesn't 500) or a live schema regen.

## 9. Key structural learnings (carry these into the next session)
1. **Merged ≠ live.** The single recurring failure here. A silent Render deploy failure and a
   branch-wiring mismatch both hid correct code behind a stale server. §7 catches both in seconds.
2. **Two schema-drift gates, two sources, two fixes** (§5). Don't hand-edit `schema-index.json` to
   silence it — regenerate from the live DB, or you mask real drift.
3. **Rule 17 keeps paying off.** A151, and several 09-02 items, were already built. Sweep source
   before building.
4. **Close on the box that serves the code.** A dev pass earns the merge; only a prod pass closes
   (rule 16). Migration state must be confirmed on *that* box.
