## 4. Changes made

**A99 · `GET /api/pos/branch-staff` (PHASE5 slice 1a, closed).** A branch NODE
gets its staff roster (with bcrypt hashes) behind a 4-condition guard
(desktop surface, node role via `x-device-id`, own business, own branch).
Additive foundation — nothing calls it destructively.

**A100 · node roster cache + `/node/verify-pin` (slice 1b, closed).** Node-only
`branch_staff` table (safeStorage-wrapped hashes), pulled on catalogue sync;
`branchStaff.ts` mirrors `pinCache` (bcrypt, scan-all, **refuse on two**) but with
**no TTL** — a node is the branch authority, roster replaced wholesale each pull.
`POST /node/verify-pin` answers a peer: identity on match, 401 final on
bad/ambiguous, 503 only when the roster can't be read. No JWT minted. Still
additive — the node can answer, no peer asks yet.

**A101 · peer authority chain + no time-bomb expiry (slice 2, BEHAVIOUR CHANGE,
closes P0 A17).** A peer's `auth:verifyPin` is now **node → cloud → cache**. The
08-08 rule holds across all three: fall back only on transport failure, never on a
rejection. The node itself falls back to its own roster. **A node-configured till
never time-expires its cache** (owner's call — "an expiry date is a time bomb");
revocation for such a till is the node roster, not a clock. A standalone till
keeps the 14-day bound. Documented tradeoff: a stolen node-configured peer kept
off-LAN can sign in a cached cashier indefinitely; physical security + §5's
typed-Windows-password rule cover the node.

**A102 · custom receipt header missing on the PHYSICAL print (closed).** The
on-screen `ReceiptView` rendered the owner's header; the thermal `renderReceipt`
did not — it printed name/branch/PIN/tel and skipped `receipt_header`. Added
`header` to `BusinessConfig`, rendered it centred under the branch name, passed
`cfg.receipt_header` into the ctx from `queueThermal`.

**A103 · till Payments tab "Something went wrong" (closed).** The A97 manager
panel hard-failed when `manage:listPaymentMethods` couldn't reach the server. It
now falls back to the till's CACHED active methods (read-only, amber note) and
hides edit controls offline. Management still needs a connection; the manager
always sees the live tenders.

**A104 · 24-hour operation — grace window + Settings tab (closes #3 & #4).** The
reported "cashier doesn't get the opening-float modal" was NOT a role bug — the
float path is role-independent. The cause was the stale-day gate: `checkDayGate`
returns `needsManager` on an unclosed prior day, which suppresses the float modal
(`needsShift && !needsManager`) for everyone, and only a manager can clear it.
Per the owner's decision, the hard lock STAYS (cash must be confirmed to close a
day), but a per-business **24-hour** setting grants a **2-hour grace window** after
midnight during which the till keeps trading behind an amber reminder — so a
cashier gets the float modal and service continues while a manager closes the day;
after the window the red lock returns. Wired like receipt text:
`continuous_operation` in `business_settings` → `/api/pos/init` → cached to
`device_config` → read by `checkDayGate`. New **Settings** tab (renamed from
Payments) holds the toggle + the payment-methods manager. `#5` (menu management)
already existed in the Menu tab — no code.

**A105 · manager-nav consolidation (closes #6 & #7).** Two pairs of sibling tabs
folded into one each, behind a shared segmented selector: **Shift** →

reported as "the manager gets the opening-float modal, the cashier doesn't," which
reads like a permission bug. It is not. `OpenDrawerModal`, `ShiftPanel.handleOpen`,

re-audit the modal for a role check; there isn't one.

rebase drill: generate a code-only patch (exclude the register), apply to a fresh
current-origin clone, re-insert the register entry above the current top,
repackage. Build patches on the *current* origin, in order.

failed on an unset secret.** The `env=unspecified` local `db:migrate` you ran
