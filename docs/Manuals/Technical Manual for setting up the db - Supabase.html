SUPABASE / POSTGRESQL 16

Setting up the SwiftPOS database

A repeatable procedure for standing up a complete, clean SwiftPOS schema on a Supabase project and confirming it matches what the codebase expects.

Audience
Backend / DevOps
Time
10–15 min
Client
psql 16.x
Result
~98 tables, RLS on all
Before production

This is the same procedure you ran in dev. For production, run it against a fresh, empty project and read Production cautions first — one step is destructive and must never touch a project that already holds data.

01 Understand

The setup model

The schema is not reproducible by replaying the numbered migrations in order. It comes together in three layers, and the runner applies them for you:

  1. Baseline — 00_baseline.sql is a full pg_dump (85 tables, RLS on every one, 94 policies) captured 2026‑07‑28. It is the starting point; the early numbered files only ALTER tables the baseline creates.
  2. Tracking — 01_schema_migrations.sql creates public.schema_migrations and backfills the state already contained in the baseline (migrations 01–18 and 21–38).
  3. Forward migrations — everything still outstanding: 19, 20, and 39 onward, applied in numeric order and recorded as they go.

On Supabase, the baseline’s dependencies — the auth schema, auth.uid(), the anon/authenticated/service_role roles, and the extensions schema — already exist, so there is no bootstrap step. (That is the one big difference from the bare‑Postgres manual.)

02 Understand

Traps & gaps a naïve run would hit

A plain psql -f *.sql loop breaks or silently mis‑tracks. The runner handles each of these; they are listed so the output makes sense.

  • 19 and 20 are not in the baseline. They were never applied historically, so they must run after it. They are the only sub‑38 files that still execute.
  • 33–38 are already inside the baseline. The files exist in migrations/ but must not re‑run; the tracking table causes them to be skipped.
  • 31 and 32 are recorded SKIPPED — numbers never used, not lost work.
  • Number gaps 62, 64, 65, 66, 68, 72 have no files. Expected.
  • 68 and 72 were applied in the historical production DB but are absent from the repo. A from‑scratch build cannot reproduce them — see Production cautions.
  • Self‑recording is inconsistent (19, 20, 53–61 don’t record themselves). The runner stamps every file uniformly so tracking is complete.

03 Prepare

Prerequisites
  • psql 16.x — the baseline uses the \restrict meta‑command that only a recent psql understands.
  • Node.js 18+ — for the verifier (verify-db-schema.mjs).
  • A Supabase project you control, and its database password.
Do not use the Supabase SQL editor for the baseline

It cannot run the \restrict / \unrestrict meta‑commands and will choke on a 7,000‑line dump. Use psql from your machine.

04 Prepare

Connection string

Use the Session pooler string: Dashboard → Project Settings → Database → Connection string → Session pooler. The username becomes postgres.<ref> and the port is 5432.

export the session-pooler URL
# Session pooler — connects as the real postgres role, works over IPv4
export DATABASE_URL='postgresql://postgres.<ref>:PASSWORD@aws-0-<region>.pooler.supabase.com:5432/postgres?sslmode=require'
Not the direct host, not the transaction pooler

The direct host db.<ref>.supabase.co is IPv6‑only and fails with “could not translate host name” on most networks. The transaction pooler (port 6543) breaks multi‑statement migrations. Session mode on 5432 is the one that works.

05 Prepare

Files you need

From the repo (or the setup package), in this structure:

layout
swiftpos/
├─ migrations/            # 00_baseline.sql, 01_schema_migrations.sql, all numbered *.sql
└─ scripts/
   ├─ setup-clean-db.sh   # the runner
   ├─ verify-db-schema.mjs # DB vs schema-index.json
   ├─ build-schema-index.sql # used by the verifier
   ├─ schema-index.json   # the expected schema
   └─ seed-admin.sql      # admin seed

06 Run

Apply the migrations
1DRY RUN

Preview the plan

Applies nothing; confirms the connection and prints what would run. The target line should show your database and role postgres.

bash
$ ./scripts/setup-clean-db.sh --dry-run

The dry run lists ~70 files because on an empty DB nothing is recorded yet. On the real run the ~34 already folded into the baseline are skipped.

2APPLY

Build the database

On a fresh, empty project this is non‑destructive — it tolerates the one redundant CREATE SCHEMA public and relies on Supabase’s existing default grants.

bash
$ ./scripts/setup-clean-db.sh

Expect a stream of → migration lines, then a summary like 36 applied, 34 already-present and a verification block (~98 tables, RLS on all, highest version recorded). Lines reading NOTICE: … already exists, skipping are the idempotency guards, not errors.

--reset is destructive

./scripts/setup-clean-db.sh --reset runs DROP SCHEMA public CASCADE before rebuilding (then restores the Supabase grants). Use it only to reclaim a dirty but disposable project — never one holding data. It prompts for the database name to confirm.

The runner is idempotent and resumable — if it stops partway, run it again and it skips what’s already applied.

3VERIFY

Confirm it matches the codebase

Diffs the live database against scripts/schema-index.json — the file the code audits every query against — and lists any table with RLS disabled.

bash
$ node scripts/verify-db-schema.mjs
# or, to also fail on extras / RLS gaps:
$ node scripts/verify-db-schema.mjs --strict

PASS means every expected table and column is present. Missing findings are critical (a half‑applied migration or the 68/72 gap). Extra findings just mean the DB is ahead of the index and are normally fine.

4SEED

Seed the admin password

Creates/resets the admin‑portal super_admin. Choose a strong password (10+ chars). Both options write a bcrypt‑cost‑12 hash the server accepts and both satisfy migration 48’s constraint that blocks the old public tutorial hash.

option A — over your psql connection
$ psql -d "$DATABASE_URL" \
     -v email="admin@swiftpos.co.ke" \
     -v pw="your-strong-password" \
     -f scripts/seed-admin.sql
option B — app-maintained script (needs apps/server/.env)
$ cd apps/server
$ ADMIN_PASSWORD='your-strong-password' npx tsx src/scripts/reset-admin.ts
Secret hygiene

Store the admin password and the project’s service_role key in your secrets manager. Option A puts the password in your shell process list while it runs; Option B reads it from the environment, which is marginally cleaner for shared machines.

07 Operate

Production cautions
Never --reset a project with data

For production, target a brand‑new project (or a verified‑empty one). Take a backup first regardless. The reset path exists for disposable environments only.

The 68 / 72 gap

Migrations 68 and 72 are recorded as applied in the historical production database but their files are not in the repo. A fresh build will not contain whatever they changed. If this new production DB must match the old one, obtain those two migrations from the current production owner and apply them before cutover; otherwise document the difference.

  • Keep the service_role key server‑side only — never ship it to any client bundle.
  • Run the verifier as the final gate before pointing the app at the new database.
  • Confirm RLS is enabled on all tables (the verifier reports this) before exposing the PostgREST/anon surface.

Troubleshooting
SymptomCause & fix
could not translate host name db.<ref>.supabase.coYou used the direct host (IPv6‑only). Switch to the Session pooler string, port 5432.
extra command-line argument … ignoredAn older copy of the runner passed the connection string positionally. Use the current setup-clean-db.sh, which passes it via -d.
