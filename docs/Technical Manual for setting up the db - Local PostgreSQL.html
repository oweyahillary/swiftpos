SELF-HOSTED / POSTGRESQL 16

Setting up the SwiftPOS database

Standing up a complete SwiftPOS schema on a bare or self‑hosted PostgreSQL 16 instance — including the bootstrap the Supabase dump silently depends on — and confirming it matches the codebase.

Audience
Backend / DevOps
Time
15–25 min
Client
psql 16.x · superuser
Result
~98 tables, RLS on all
Read the scope section first

The baseline is a Supabase dump. On bare Postgres it needs a bootstrap prelude, and some Supabase services (Auth, the auto REST API, Realtime) are simply not present. What that means for you →

01 Understand

The setup model

The schema is not reproducible by replaying the numbered migrations in order. It assembles in layers, and — apart from the first — the runner applies them for you:

  1. Bootstrap (local only) — 00_prereqs_local.sql creates the roles, schemas, extensions, and auth shim the dump assumes already exist. You run this once, first.
  2. Baseline — 00_baseline.sql, a full pg_dump (85 tables, RLS on every one, 94 policies) from 2026‑07‑28. The starting point; early numbered files only ALTER what it creates.
  3. Tracking — 01_schema_migrations.sql creates public.schema_migrations and backfills the state already in the baseline (01–18, 21–38).
  4. Forward migrations — everything outstanding: 19, 20, and 39 onward, in order, recorded as they go.

02 Understand

What bare Postgres does & doesn’t give you

The baseline references Supabase primitives it never creates: auth.uid() (used by 150 RLS policies), foreign keys into auth.users, the roles anon / authenticated / service_role, and extensions.uuid_generate_v4(). The bootstrap in step 1 provides minimal stand‑ins so the schema loads.

Services are not the same as schema

This procedure provisions the database. Supabase Auth (the owner dashboard login), the PostgREST auto‑API, and Realtime are separate services a bare Postgres does not run. Use this path only if either:

  (a) you run self‑hosted Supabase — then connect to its bundled Postgres and follow the Supabase manual, not this one; or

  (b) your API server connects with a privileged / BYPASSRLS role and you do not depend on Supabase Auth for sign‑in.

The auth shim is a stub

auth.uid() returns a per‑session GUC (or NULL), and auth.users is an empty table that only satisfies the foreign keys. If you later attach real authentication, replace the stub with the genuine auth schema before going live.

03 Understand

Traps & gaps a naïve run would hit
  • 19 and 20 are not in the baseline — they run after it, and are the only sub‑38 files that still execute.
  • 33–38 are already inside the baseline — the files exist but must not re‑run; tracking skips them.
  • 31 and 32 are recorded SKIPPED — numbers never used.
  • 62, 64, 65, 66, 68, 72 have no files — expected gaps.
  • 68 and 72 were applied in the historical production DB but are absent from the repo — a fresh build cannot reproduce them. See Production cautions.
  • Self‑recording is inconsistent — the runner stamps every file uniformly so tracking is complete.

04 Prepare

Prerequisites
  • PostgreSQL 16 server you can reach, and a superuser login — CREATE ROLE and CREATE EXTENSION require it.
  • psql 16.x — the baseline uses the \restrict meta‑command.
  • Node.js 18+ — for the verifier.
  • The uuid-ossp and pgcrypto contrib extensions available to the server (standard in most distributions / postgresql-contrib).

05 Prepare

Connection string

Connect as the superuser to the target database. Create the database first if it doesn’t exist.

create db + export URL
$ createdb swiftpos            # or: CREATE DATABASE swiftpos;
export DATABASE_URL='postgresql://postgres:PASSWORD@localhost:5432/swiftpos'

07 Run

Provision the database
1BOOTSTRAP

Run the prereqs prelude (as superuser)

This is the step that makes the Supabase dump loadable on bare Postgres. It creates the anon/authenticated/service_role roles, the extensions schema with uuid-ossp and pgcrypto, and the auth schema with a users stub and an auth.uid() shim.

bash
$ psql -d "$DATABASE_URL" -f scripts/00_prereqs_local.sql

Run it once per database, before the runner. It is idempotent — safe to re‑run.

2DRY RUN

Preview the plan

Applies nothing; confirms the connection and lists what would run. The target line should show your database and role postgres.

bash
$ ./scripts/setup-clean-db.sh --dry-run

The dry run lists ~70 files because on an empty DB nothing is recorded yet; the real run skips the ~34 already folded into the baseline.

3APPLY

Build the database

On a fresh database the default (non‑reset) mode is correct: public already exists empty, so the runner strips the one redundant CREATE SCHEMA public and applies the rest.

bash
$ ./scripts/setup-clean-db.sh

Expect a stream of → migration lines, then 36 applied, 34 already-present and a verification block. NOTICE: … already exists / does not exist, skipping lines are idempotency guards, not errors. The runner is resumable — re‑run if it stops partway.

--reset is destructive

--reset runs DROP SCHEMA public CASCADE before rebuilding, then re‑grants the app roles. Use it only on a disposable database, never one holding data. It prompts for the database name to confirm.

4VERIFY

Confirm it matches the codebase

Diffs the live database against scripts/schema-index.json and lists any table with RLS disabled.

bash
$ node scripts/verify-db-schema.mjs
# or, to also fail on extras / RLS gaps:
$ node scripts/verify-db-schema.mjs --strict

PASS means every expected table and column is present. Missing findings are critical; extra findings mean the DB is ahead of the index and are normally fine.

5SEED

Seed the admin password

Creates/resets the admin‑portal super_admin. Choose a strong password (10+ chars). The seed uses pgcrypto (installed by the bootstrap) to write a bcrypt‑cost‑12 hash the server accepts, and it avoids the retired public tutorial hash so migration 48’s constraint is satisfied.

bash
$ psql -d "$DATABASE_URL" \
     -v email="admin@swiftpos.co.ke" \
     -v pw="your-strong-password" \
     -f scripts/seed-admin.sql
Secret hygiene

Store the admin password in your secrets manager. The value is visible in the process list while psql runs; on shared hosts prefer a wrapper that reads it from the environment.

08 Operate

Production cautions
Replace the auth stub before real sign-in

The bootstrap’s auth.users / auth.uid() are placeholders. If production will authenticate real users, wire in genuine authentication (self‑hosted Supabase/GoTrue or your own) and ensure auth.uid() returns the real subject before exposing any RLS‑gated surface.

The 68 / 72 gap

Migrations 68 and 72 are recorded as applied in the historical production database but are absent from the repo. A fresh build will not contain their changes. If this new DB must match the old one, obtain those migrations from the current production owner and apply them before cutover; otherwise document the difference.

  • Give the API server a role that mirrors service_role (BYPASSRLS) — or connect it as the owner — so RLS behaves as designed. Do not hand out that role to clients.
  • Take a base backup and set up WAL archiving / point‑in‑time recovery before go‑live.
  • Run the verifier as the final gate before pointing the app at the database.

SymptomCause & fix
function extensions.uuid_generate_v4() does not existBootstrap not run, or uuid-ossp not installed into the extensions schema. Run 00_prereqs_local.sql as superuser.
schema auth does not exist / relation auth.users does not existBootstrap not run. It creates the auth schema and the users stub.
