POS screens: one design for both POS

Prepared 4 Nov 2026 from the code on dev. The desktop POS is the base, because most customers use it. Each screen lists what the desktop already does (kept as it is), the web POS features I suggest adding, and the points where you need to choose. Tick or untick, then press Copy my choices and paste the result to Claude.

Decided by the owner, 4 Nov 2026.
  • Payment: quick cash buttons, tip buttons (5 / 10 / 15 %, custom), split evenly per person, split by item per guest, loyalty points shown. Not added: receipt preview / Print again, a customer name box.
  • Cart: courses with Held / Fires now and Fire course; Print bill, Transfer, Split bill and Room on the desktop too (premium). Variants as chips.
  • Product tile: "Sold out", "Later"; the word "Options".
  • Forecourt: Activate pump stays, and the desktop gets it too.
  • Small screens: smaller type or extra buttons are fine, but the screens must not look cluttered or become hard to find your way around. A feature a business does not use stays out of sight (courses only for restaurants, Room only for hotels, the fuel pieces only on a forecourt).
How it will be built. After the shared-components branch is merged into dev, one screen at a time, starting with the payment screen. Each screen is built once and used by both POS. On a phone or tablet the web POS keeps its own layout of the same screen (for example the cart as a full-screen sheet). New features load only when needed, so the desktop POS's start-up code stays inside its size limit.

1. Payment screen

Kept from the desktop POS

  • One card per payment with + Split payment; every part can be any method, M-Pesa prompt and On account included.
  • A reference on every non-cash payment (the web asks for none on a single card payment).
  • M-Pesa prompt inside the payment screen: once the customer pays, the sale completes and prints by itself.
  • M-Pesa Payments received: tap the payment, the sale completes.
  • On account: search the customer here, see the limit, what they owe and what is left; the approver's PIN is asked before the sale.
  • Manual discount, amount or %, capped at the role's maximum with "Ask a manager" (the web has no discount box today).
  • The customer screen follows the payment.
  • Delivery platform sales (Glovo and others) at platform prices, with the order number.
  • Exact amounts: the parts must add up to the bill, cash given must cover the cash part.

Add from the web POS

Not offered: the web's WhatsApp receipt button (it only shows a "set up the WhatsApp provider" message today) and its eTIMS signature check (eTIMS is parked; clients file it themselves).

2. Cart lines

Kept from the desktop POS

  • Variants and add-ons as small chips on the line (the web does not show add-ons on the line at all).
  • The kitchen mark: 🍳 once sent, "2 sent" when only part went.
  • The note button hidden once a line went to the kitchen; tapping a noted item makes a new line.
  • The stricter kitchen rules: taking any sent quantity off, removing a sent line or clearing a sent order always goes through the kitchen void (reason, made or not, manager PIN when that switch is on). Extra added after a send comes off freely.
  • Hold (restaurants) with the held-orders count; "+ Customer" in the cart header.
  • Price each, per litre or per kg; fuel and weighed lines cannot have their quantity changed.

3. Product tile

Kept from the desktop POS

4. Forecourt

Kept from the desktop POS

  • Pump cards drawn as dispensers: grade colour, state (Idle, In use, Off, No price), the last sale, price per litre, litres today.
  • A gauge per grade: the tank level with a low mark (online licence), otherwise litres today against yesterday.
  • The fuel keypad: KES or litres with the other worked out live, 500 / 1,000 / 2,000 and Full tank; a USB number pad works too.
  • Pumps / Shop tabs.

Also found while comparing

  • The web POS has no manual discount box at the moment (its discount panel exists but is never shown). The shared payment screen brings the desktop's back to the web.
  • The web's split payment cannot send an M-Pesa prompt; the desktop's can. Fixed by the shared screen.
  • Old web files no screen uses: PetrolPOS.tsx, and the unused discount and loyalty panels. Removed during the work.
