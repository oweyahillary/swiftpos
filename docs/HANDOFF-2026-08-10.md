## 4. Changes made

### The empty `user_devices` table had THREE independent causes
Each fixed alone showed **no visible change**, which is why it took the afternoon
and three wrong diagnoses.

- **D14** — registration sat behind an opt-in flag (`auth.ts:432`) with owners
  exempt, so a desktop till fell through both gates. Measured: one
  `require_device_registration` row in the entire database (Lovers Rock, false).
  Nobody ever switched it on, so `deviceBinding.ts` (181 lines) and
  `devices.ts` (216 lines) were dead code in production.
- **A36 (P0)** — `/desktop-login` minted `surface: 'web'` while the file header
  had said `surface='desktop'` since the route was written. It propagates via
  `/verify-pin`, so **four features were silently off on every till**:
  `offlineAuth` (hence the empty PIN cache), device registration, the
  `desktop_licensed` gate, and `requireWebSurface`.
- **A38** — the till sent `X-Device-Id` **twice** (`'x-device-id'` and
  `'X-Device-Id'` in one object literal), so the cloud received them
  comma-joined and truncated. `WHERE device_id = ?` could never match. Found in
  Render's log, not by reading.

### Printing — the thread is closed
- **D8 closed.** Thermal ran a full service including dispatch slips, so the
  HTML **sale** path is gone. D8 is closed **by reporting**: `printSale` always
  returned `{ queued, skipped }` and every caller discarded `skipped`; it now
  reaches the cashier as *"nothing printed for: Dispatch"*.
- `escpos_enabled` defaults **ON** with a guarded one-time backfill. Verified
  against real SQLite: runs once, and does **not** override a deliberate off.
- **Kept deliberately:** shift/Z-reports, calibration, previews. `escposBridge`
  exports exactly one print function — there is no thermal shift report.

### Beryl's eight orders — resolved, and not what anyone thought
Not lost. Re-pushed on 08-08 at 15:18 and **dated 8 August**, because the
offline-dating fix (`a4aee05`) had shipped to the till and its cloud half sat
unmerged on `dev` for five days. 7 August is booked at 13,060; the evening
actually took 31,930. Dev data, so a reporting curiosity rather than a client's
books. **The original 21:09-22:53 cause is still unknown** — A15 means a
recurrence now names its own SQLSTATE.

## 5. Failed attempts — read this before re-deriving anything

**Three wrong diagnoses of the Beryl failure, in order.** Each was confidently
argued from source and each was wrong:

1. "Something threw after the RPC committed." Ruled out: the till sends a stable
   `X-Idempotency-Key` and `orders.ts:360` short-circuits, so a committed order
   would have cleared at `attempts=2`, not 5.
2. "A14 — the owner token carried an `auth.users` id, so `cashier_id` failed
   23503." Ruled out by query: all three `cashier_id` values exist in
   `public.users`. **A14 is a real latent bug and was fixed, but it was not this.**
3. "Cashier `2ee6adfe` has exactly 8 orders — those are them." Coincidence.
   They span 22 July to 4 August.

**What actually worked was executing things, not reading them.** Every real bug
today — 42P16, the Windows path, migration 47 never running, the unwired suite,
the duplicated header, `surface: 'web'` — surfaced by running or by a production
log. Careful reading caught none of them.
