## 2. Tonight's build — offline table-move + fire-course (restaurant)
**Why:** I audited what a restaurant can do during an outage. The money paths all buffer already (orders, pay, void, refund, expense, wastage, shift open/close/drawer/movement). The gap was two **restaurant** operations that were **refused offline**: moving an open order to another table, and firing a held course to the kitchen. For the restaurant segment we're marketing, that's a real hole in "the till keeps selling offline."

**Fix:** both now buffer offline and replay on reconnect.
- They're **idempotent**, so a replay is safe: `move-table` sets the table (last write wins); `fire-course` only fires still-`held` items (a replay finds none → no-op).
- On the server, both now resolve the till's own order id via `cloudOrderId` — the **same proven pattern** void/refund/pay already use — so an order created offline (known only by its tablet uuid) is found when the move/fire replays after it.

**Files changed (5):**
- `packages/core/src/tillBuffer.ts` — new `order_op` buffer kind + two write routes (`/orders/:id/move-table`, `/orders/:id/fire-course`).
- `apps/server/src/routes/orders.ts` — `cloudOrderId(req.params.id, …)` in both routes.
- `tests/till-buffer-stage2.test.mjs`, `tests/table-move-kitchen.test.mjs`, `tests/android-till-stage2.test.mjs` — new assertions.

**Blast radius:** `bufferableKind` is used **only by the Android app** (the desktop has its own offline system), so this changes Android offline behaviour only. The server change is **additive** — online (web POS) is unchanged because `cloudOrderId` resolves the server id first.
