The fix already lived in `PinPage.tsx`: the reveal field's `onPaste` detects an `st2.` token,

## A186 — Windows migration false-FAIL (FIX BUILT, PARTIAL, unverified)
The Windows crash (`Assertion failed: !(handle->flags & UV_HANDLE_CLOSING), src\win\async.c`) fires
during process teardown when a migration test exits with its PGlite native handle still open. Fix:
close the handle before exit so libuv has nothing to crash on — the pattern the tests that already
survive Windows (75–85) use.

Applied `await db.close().catch(()=>{})` before `process.exit` in the **6** migration tests that
hold a single long-lived `db` in scope at exit:
`test-migration-{47,50,51,52,100,101}.mjs`.

**Two candidates could NOT take the fix — left untouched:** `test-migration-48.mjs` and
`test-migration-99.mjs` use multiple block-scoped `{ const db = … }` instances, so there is no
single `db` in scope at the exit line. A first attempt added the close there and broke both with a
ReferenceError; the Linux suite caught it and both were reverted to pristine.

**This is unverifiable here (rule 16).** The crash is Windows-only; the full migration suite passes
on Linux with AND without this change, so I cannot prove it fixes anything. The proof is on the
owner's Windows box:
- Run `node scripts/run-all.mjs`. If the migration suite no longer false-FAILs → the fix works,
  move A186 to CLOSED.
- If it STILL false-FAILs → tell me exactly which `test-migration-*.mjs` files crash; if 48 or 99
  are among them, I'll fix those two specifically (they need a different shape — close each
  block-scoped db, or restructure to one instance).

A186 is already P3 (CI on Ubuntu is the authoritative green; this is a local-Windows cosmetic
annoyance), so shipping a partial, unverified fix here carries no risk to the gate signal.
